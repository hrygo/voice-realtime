## 2026-09-01 SpeechRail 与运行时工作负载契约（优先于全文其他描述）

本节记录已经落地的服务端运行契约；2026-08-17 的选型调研与 2026-08-21 的历史实测继续保留，
但凡涉及模式、普通字幕连接、SRT 或控制 WebSocket 的描述与本节冲突，均以本节为准。

SpeechRail 独立负责 ASR/TTS 模型、profile、worker 与健康状态。`sona` 只负责 AudioHub
采集、PCM owner 仲裁、OpenAI Realtime 客户端适配、窗口/epoch 对账、播放/取消和业务持久化；OpenAI Realtime
连接不可透明恢复，断线后必须创建新会话并由应用执行 source epoch/窗口收敛。

### 四模式与单一 PCM owner

`RuntimeModeCoordinator` 是唯一 workload 仲裁者。服务进程和模型可以常驻预热，但稳定状态下 PCM
只能由一个 workload 接收：

| mode | `PCMOwner` | 允许消费 PCM 的链路 |
|---|---|---|
| `assistant` | `assistant` | SpeechRail ASR → LM Studio → SpeechRail TTS 交互链路 |
| `subtitles` | `subtitles` | 普通字幕 SpeechRail `/v1/realtime` capture |
| `meeting` | `meeting` | 会议 SpeechRail capture、分人和 PostgreSQL 对账 |
| `idle` | `none` | 无推理链路 |

切换顺序固定为 target prepare（连接可 ready，但不接收 PCM）→ owner `none` 屏障 → 来源 quiesce/drain
→ 同步激活目标 → 原子提交 `mode/pcm_owner/runtime_revision` → 单次稳定广播。目标准备失败时来源保持不变；
屏障后的失败优先补偿恢复来源，恢复失败则全停并进入 `idle/none`。普通用户命令串行且不互相抢占；
shutdown 可以取消在途转换，但必须 abort prepared target、尽力停止全部 workload，并用一次稳定广播
落地最终状态。

### 服务端口与控制拓扑变更

- 主服务统一为 `sona-ui`（默认 `127.0.0.1:8100`），托管全部 HTTP、静态资源与 WebSocket。
- TTS 由 SpeechRail 提供（默认 `127.0.0.1:8201`），交互播放使用 `/v1/realtime`，试听/目录使用
  `/v1/audio/speech` 与 `/v1/voices`。
- SpeechRail（默认 `127.0.0.1:8201`）由 `SubtitleProxy` 按需建立 `/v1/realtime` transcription
  session；前端和外部客户端一律不直连 ASR worker。
- 外部只读字幕订阅收敛到 `sona-ui` 的 `/ws/subtitles`；只有 `subtitles` 或 `meeting` 模式下该连接才合法，
  在 `assistant` 或 `idle` 模式下连接会被拒接或断开（code 4409）。
- 控制面统一为 `/ws/v1/control`（保留 `/ws/assistant/cmd` 别名），会议事件流统一为
  `/ws/v1/{control,meetings}`；运行与联调见 [`../manuals/会议助手后端运行与前后端联调.md`](../manuals/会议助手后端运行与前后端联调.md)。
- 运行时模式互斥使得单机免提场景下的回声天然降级：会议与普通字幕运行时交互助手完全停止，
  不再产生 Agent TTS 外放被自身字幕转录的死循环；交互模式下的回声防御继续由
  `EchoSuppressionProcessor` 与 `SelfEchoFilter` 承担。

### SubtitleProxy、控制通道与只读字幕订阅

- `SubtitleProxy.start()` 只初始化代理并进入 paused，不激活普通字幕连接。进入普通字幕必须向
  `/ws/v1/control` 或 `/ws/assistant/cmd` 发送 `start_subtitles`，由服务端完成 prepare/commit。
- `/ws/v1/control` 与 `/ws/assistant/cmd` 都持续向每个连接广播完整 `runtime_state`。命令 ack 只发给
  请求连接；ack 与广播没有固定顺序。服务端接受命令后，即使请求连接断开，转换也继续执行。
- `/ws/subtitles` 是只读事件订阅，建连不会抢占模式。仅 `subtitles` 或 `meeting` 合法；非法建连或
  存续期失去资格时固定关闭 `4409`，reason 为“字幕模式未激活”。`subtitles → meeting` 可保持连接，
  `meeting → idle` 必须撤销连接。
- 会议结束、异常中止或 finalization 超时后进入 `idle/none`，不自动恢复普通字幕或语音助手。

### 普通字幕 SRT epoch

每次普通字幕激活以及活动模式重连都会创建递增的连接 epoch。每个 epoch 的 confirmed 最多归档一次；
关闭 epoch 时，`current.srt` 通过同目录临时文件原子替换为空，同时清除旧 payload 与签名，因此新客户端
不会收到上一 epoch 的旧快照。没有 confirmed 的 epoch 不生成归档。会议 capture 使用独立数据边界，
永不写普通字幕 `current.srt` 或普通字幕归档。

### 进程健康与 workload 诊断

`GET /api/services` 的 SpeechRail HTTP `status` 与 `workload/ws_state` 独立。SpeechRail 条目新增
`workload`、`ws_state`、`reconnect_count`、`last_event_age_ms`；顶层 `diagnostics` 固定包含
`audio_hub`、`interaction`、`subtitles`、`tts`、`last_transition`。长时间静音只增加事件年龄，
不自动把 ready workload 判为 degraded。TTS 只记录 `first_chunk_ms`、`chunk_count`、
`max_source_chunk_gap_ms`、`median_source_chunk_gap_ms`、`source_chunk_gaps_over_200ms` 等原始源块节奏；
系统不扫描游戏或其他进程，也不基于这些字段自动做资源归因。

### 历史发布前真实闭环（2026-08-26，SpeechRail 迁移前）

以下记录来自 SpeechRail 迁移前的运行时仲裁验证，仅证明当时应用状态机与旧语音链路的行为；其中的
延迟、重连和“未 ready”数据不能替代当前 SpeechRail 服务的部署、模型/profile 就绪和真实音频闭环验收。

本轮在同一台笔记本分别使用 localhost 和 `run-all.sh` 输出的实际 LAN IP 执行；复现步骤如下：

```bash
# localhost
scripts/run-all.sh
curl --fail --silent http://127.0.0.1:8100/api/runtime | python3 -m json.tool
curl --fail --silent http://127.0.0.1:8100/api/services | python3 -m json.tool

# 停止 localhost 轮次全部子进程后执行 LAN
SONA_BIND_HOST=lan scripts/run-all.sh
# 在同一台笔记本上，将示例地址替换为 run-all.sh 输出的实际 LAN IP
SONA_LAN_IP=192.0.2.10
curl --fail --silent "http://${SONA_LAN_IP}:8100/api/runtime" | python3 -m json.tool
curl --fail --silent "http://${SONA_LAN_IP}:8100/api/services" | python3 -m json.tool
```

两轮都应人工覆盖 `assistant → subtitles → assistant`、活动字幕断线重连、双浏览器相反命令、
`subtitles → meeting → idle` 和 SpeechRail 未 ready。记录时间、最高 revision、mode、owner 与 drop/gap 计数，
不记录音频或完整转写。LAN 轮次在同一台笔记本使用 `run-all.sh` 输出的实际 LAN IP 访问 `8100`，
不可用 localhost 代替；若未来有第二设备，可作为可选扩展验证，但不是发布门禁。前后端必须同版发布和整体回退；
`/api/services` additive 字段可被旧客户端忽略，回退时不得删除任何 interrupted meeting record。

本轮 localhost 权威状态按 `assistant/assistant@1 → subtitles/subtitles@2 → assistant/assistant@3 →
meeting/meeting@4 → idle/none@5` 收敛；LAN 最终一轮按 `assistant/assistant@5 →
subtitles/subtitles@6 → assistant/assistant@7` 收敛。两个控制连接收到相同 revision，字幕未激活和存续期
撤销均返回稳定 `4409`。localhost 与 LAN 的 TTS 首块分别为 `287.8ms`、`271.5ms`，最大源块间隔分别为
`45.3ms`、`44.7ms`，两轮 `source_chunk_gaps_over_200ms=0`。文本注入验证了 LM Studio → TTS →
输出帧链路；Agent 未将无法听觉确认的扬声器音量表述为人工听到。临时会议在 PostgreSQL 中为
`completed`，结束后保持 `idle/none`。

故障注入进一步验证：SpeechRail 未 ready 时字幕和会议切换均不抢占 assistant，prepared meeting 持久化为
`interrupted/mode_switch_aborted`；活动字幕断线时 workload 为 `degraded/backoff`，控制命令继续可用，
服务恢复后 `reconnect_count=5` 且回到 `ready/connected`。`subtitles → meeting` 保持既有只读连接，
`meeting → idle` 再关闭 `4409`；并发相反命令最终收敛到单一 `assistant/assistant@7`。runtime 目录未产生
音频制品。无 confirmed 的 epoch 不生成 SRT 归档，其余 SRT epoch 隔离由自动化回归覆盖。

## 2026-08-21 落地架构校正（历史记录；当前边界以 2026-09-01 契约为准）

本文保留 2026-08-17 的选型调研过程；本节仅供历史溯源，凡与上方 2026-09-01 契约或当前代码冲突之处，
以当前契约和代码为准。以下早期选型表、
成熟度调研和附录属于历史记录，不代表当前部署依赖；当前 ASR/TTS 统一由 SpeechRail 提供。

- 默认运行三个应用/基础设施单元：LM Studio、SpeechRail、`sona-ui`；ASR/TTS 与可选
  Sortformer 是否启用由 SpeechRail profile 决定，`sona` 不启动本地 ASR/TTS worker。
- `sona-ui` 拥有唯一麦克风、AudioHub、注入式 Pipecat 管道和 SubtitleProxy。
- `sona-interact` 是 headless 替代入口，与 `sona-ui` 由 `InteractionOwnership` 文件锁互斥，
  绝不能作为第五个并行服务。
- 字幕音频由 SubtitleProxy 以 16kHz mono int16 PCM 发送；SpeechRail 负责 profile、窗口和
  transcription event 生成，应用只负责 epoch/offset 与快照边界。
- 默认禁止 TTS、交互 STT 与字幕 ASR 隐式联网下载；缓存或本地目录缺失时 fail-fast。
- 新增会议助手互斥模式：会议中停止交互 LLM/TTS，只做带匿名 speaker 的持续转录；结束后使用
  `qwen/qwen3.6-35b-a3b` 原生 `/api/v1/chat`、`reasoning:"off"` 生成带证据 UUID 的纪要。
- 会议不保存音频，也不写普通字幕 SRT；confirmed 文本、speaker 与纪要持久化到本机 PostgreSQL
  `sona` 独立 schema，数据库不可用时普通助手仍可运行但禁止开始会议。
- 前后端以 `contracts/meeting-assistant/v1/` 为唯一契约，独立前端使用 `/api/v1/*` 与
  `/ws/v1/{control,meetings}`；运行与联调见 `会议助手后端运行与前后端联调.md`。
- 项目现在包含必要的运行时胶水：有界音频扇出、会话生命周期、控制/状态协议、重连、
  快照去重和原子 SRT 持久化，不再把 TTS 桥描述为“唯一自研代码”。
- 会议捕获结束、中止或最终化超时后进入 `idle/none`，SubtitleProxy 不自动恢复普通字幕 supervisor，
  语音助手也不自动恢复。
- LM Studio 继续使用原生 `/api/v1/chat`、`reasoning:"off"`；交互首轮以独立
  `system_prompt` + 当前 user `input` 建链，后续用 `previous_response_id` + 当前 `input`
  续接真实角色历史。payload 不发送 `role`/OpenAI `max_tokens`，OpenAI 兼容端点不能关闭推理；
  长会话以结构化记忆后台预热并原子换链，原生摘要上限使用 `max_output_tokens`。
- ASR/TTS 均由 SpeechRail 负责模型 worker 串行化与有界队列；TTS 固定 24kHz，请求级 preset 生效，
  sona 只管理客户端会话、播放与取消。
- 质量门禁命令沿用项目当前的 pytest、mypy、ruff、前端测试与构建流程；测试数量以最近一次完整验证输出为准，
  不在架构文档中固化易过期的计数。

当前权威拓扑、控制协议与运行命令分别见 [`系统总体架构与详细设计方案.md`](系统总体架构与详细设计方案.md)、
[`../manuals/Sona-UI-设计方案.md`](../manuals/Sona-UI-设计方案.md) 和项目 [`../../README.md`](../../README.md)。

### 架构(定稿)

```
WhisperLiveKit ──► 实时字幕(Web UI + SRT + 说话人分离)
   │ Qwen3-ASR streaming (MPS 原生)
   ▼
Pipecat ── FunASR(SenseVoice) ──► LM Studio 35B-A3B ──► [qwen3-tts-openai 桥] ──► Qwen3-TTS --stream ──► 播放
   │
   └─ WebSocket / localhost(单机、无外网依赖、128GB 内存无压力)
```

### 验收门槛(达标才收工,详见 §7)

- 字幕:说话 1s 内出 partial、2s 内 confirmed;中文专名/数字/ITN 正确
- 交互:端点判定后 TTFA < 2s(目标 < 1.5s);连续 20 轮无卡死/重复
- 资源:语音链路常驻 < 15GB,与 LM Studio 三实例共存

### 明确不做

- 不自研 ASR 模型与解码器；仅实现必要的快照适配、重连、控制 WS 和 SRT 持久化
- 不引入 livekit/agents(多用户/电话场景才需要)
- 不用 faster-whisper(CTranslate2 在 Mac 无 GPU 加速)、openasr(1 star 未验证)

## 0. 需求与目标

| 场景 | 核心要求 | 延迟预算 |
|---|---|---|
| **实时语音交互**(语音助手式对话) | 边说边出中间结果、说话结束即响应、TTS 流式回读 | 端到端对话 < 2s;TTS 首包(TTFA)< 300ms |
| **实时语音字幕**(会议/直播/本地音频实时转写) | 部分结果(partial)+ 最终结果(confirmed)两级文本、带时间戳、可流式输出 | 首条 partial < 1s;确认文本滞后 < 2s |

**两条硬约束推导出的选型原则**:
1. **流式是硬指标** → 一切"整段音频一次性处理"的模型(如 SenseVoice llama.cpp 运行时)**不能**做实时主链路,只能做批处理兜底
2. **Apple Silicon 是硬约束** → 全栈走 **MLX / llama.cpp(Metal)原生**,排除 PyTorch-CUDA 中心方案(CTranslate2 系在 Mac 仅 CPU,同样出局)

## 1. 总体架构

```
                    ┌─────────────────────────────────────────────┐
 麦克风/系统音频 ──▶ │  VAD/端点检测(能量 / FSMN-VAD / Silero)      │
 (16kHz PCM 分块)   └───────────────┬─────────────────────────────┘
                                    ▼
                    ┌─────────────────────────────────────────────┐
                    │  流式 ASR(增量解码,滚动窗口)                  │
                    │  mlx-qwen3-asr(主) / sherpa-onnx(备)        │
                    └───────────────┬─────────────────────────────┘
                                    │ partial + confirmed + 时间戳
                    ┌───────────────▼───────────────┐             │
                    │ 字幕服务(SSE/WebSocket)        │             │
                    │  partial:浅色可修正             │             │
                    │  confirmed:追加定稿            │  (可选)CAM++ 说话人分离
                    └───────────────┬───────────────┘             │
                                    │ 整句(端点判定后)             ▼
                    ┌───────────────▼───────────────┐   ┌────────────────────┐
                    │  LLM 对话(LM Studio 35B-A3B)   │   │  字幕渲染 UI        │

                    └───────────────┬───────────────┘   └────────────────────┘
                                    ▼
                    ┌─────────────────────────────────────────────┐

                    │  Qwen3-TTS --stream(主)/ CosyVoice3-MLX(备) │

```

**唤醒词(可选)**:`sherpa-onnx-kws`(流式 zipformer KWS)常驻监听,命中后才激活交互链路,避免全时 ASR 资源占用。

## 2. 组件选型(实时优先)

### 2.1 流式 STT(实时字幕 + 交互的耳朵)

| 方案 | 类型 | 中文精度 | 实时能力 | Apple Silicon | 定位 |
|---|---|---|---|---|---|
| **mlx-qwen3-asr**(moona3k) | MLX 重实现 | 最强(超越 Whisper-large-v3;30 语 + 22 中文方言) | ✅ **真流式**:KV-cache 增量解码、2s 块滚动、energy 端点、`stable_text` 单调 | ✅ 原生 | **实时主链路首选**:自带 `--mic` 实时麦 + OpenAI 兼容 HTTP 服务 |
| mlx-audio Qwen3-ASR 1.7B | MLX | 强(中文 CER 6.8-7.7% 同级最低) | ⚠️ 窗口重解码(非原生增量),`--stream` 出 partial | ✅ 原生 | 批处理/高质量兜底;partial 可作次级字幕源 |

### 2.2 流式 TTS(交互的嘴)

| 方案 | 首包延迟 | 中文质量 | 实时能力 | 定位 |
|---|---|---|---|---|
| **Qwen3-TTS 1.7B**(mlx-audio) | 低(推理 ~97ms 级) | 顶尖(Seed-TTS 中文 WER 0.77) | ✅ `--stream` 边生成边播;自然语言语音指令 | **主推**:MLX 原生、一条命令 |
| CosyVoice 3(MLX 移植 ~1.1GB) | **150ms**(文档值) | SOTA(18 方言、3s 克隆) | ✅ 双向流式 | 方言/克隆/流式极致场景 |
| Kokoro-82M(mlx-audio) | ~80ms 级 | 良(非中文强项) | ✅ `--stream` | 轻量英文/快速响应 |
| IndexTTS2(MPS) | 中 | 情感/多音字天花板 | ⚠️ 非流式 | 创作级离线合成,不用于实时交互 |

**结论**:实时交互 TTS 用 **Qwen3-TTS(mlx-audio `--stream`)**,首包快、中文顶尖、可自然语言控语速语气;若需方言或更低 TTFA,切 CosyVoice 3。

### 2.3 VAD / 端点检测

| 方案 | 说明 | 用途 |
|---|---|---|
| **energy 端点**(mlx-qwen3-asr 内置) | 低能量边界选切分点 | 交互"说话结束"判定 |
| FSMN-VAD(FunASR) | 语音活动检测,30s 单段上限 | 长音频分段(批处理) |
| Silero VAD(whisper.cpp / sherpa-onnx) | 通用 VAD | 字幕降噪、静音跳过 |

交互端点经验值:静音 **500-800ms** 判定一句话结束;单句上限 30s 强制切分。

### 2.4 LLM(交互大脑)

沿用现有栈:`lmstudio/qwen/qwen3.6-35b-a3b`(context 262144)。对话场景固定 **thinking 关**
(`/api/v1/chat` + `reasoning:"off"`)，短响应优先。原生 payload 不支持 OpenAI `max_tokens`；
需要限制后台摘要/预热输出时使用已实测支持的 `max_output_tokens`。

## 4. 实时参数与延迟预算

| 环节 | 目标 | 手段 |
|---|---|---|
| ASR partial 首出 | < 1s | 2s 块滚动解码;`delayPreset` 类参数偏 `latency` |
| ASR confirmed | < 2s | `finalization_mode="accuracy"`(默认)或 `"latency"` 二选一按场景 |
| 端点判定 | 静音 500-800ms | energy 端点 / VAD 参数 |
| LLM 首 token | < 300ms | 35B-A3B TTFT 0.08-0.28s;thinking 关 |
| TTS TTFA | < 300ms | Qwen3-TTS `--stream`;必要时 CosyVoice3 150ms |
| 端到端交互 | < 2s | 上述环节串联,瓶颈在 ASR 确认 + LLM 生成 |

**字幕双级模型**(mlx-qwen3-asr `stable_text` 设计):`partial` 只增不改(浅色),`confirmed` 单调追加(定稿)——UI 按此渲染,避免整句跳动。

### 7.2 关键实测结论(实现时已锁定,勿回退)

1. **LM Studio 推理开关**:OpenAI 兼容 `/v1/chat/completions` 端点**忽略** `reasoning` 参数;
   唯一有效路径是**原生 `/api/v1/chat`**(`reasoning:"off"` 实测 `reasoning_output_tokens=0`)。
   原生端点不接收 OpenAI `messages` 历史：首轮发送 `system_prompt` + 当前 user `input`，
   后续发送 `previous_response_id` + 当前 `input`；只在 `chat.end` 提交 response ID，
   从而保留真实 system/user/assistant 角色。payload 不发送 `role`/OpenAI `max_tokens`，正文 SSE
   事件为 `message.delta`；非流式响应为 `output[].content`（**非** OpenAI `choices`）。原生
   `max_output_tokens` 已实测可与 `store:false`、`reasoning:"off"` 同时生效。
2. **长会话上下文压缩**：Pipecat 保留完整角色历史，应用以原生 `input_tokens`、TTFT、未压缩
   消息数和模型容量触发后台结构化摘要。摘要 `store:false`，预热新链只接受精确
   `MEMORY_READY`、零 reasoning tokens 和合法 response ID；generation、完成轮数或旧 ID 变化时
   丢弃候选。默认 soft/hard/target 为 16384/32768/8192 tokens，保留最近十六组完整问答；
   短消息兜底为 128 条，连续 TTFT 触发为 3 秒；
   `SONA_INTERACTION_CONTEXT_COMPACTION_ENABLED=false` 可回滚。断链恢复失败时明确报错，不空链降级。
3. **SenseVoice 下载源**:funasr 的 `hub` 参数被 pipecat `FunASRSTTService` 硬编码为 modelscope(`ms`),
   该站在本环境被 SSRF 拦截 → **统一经 `snapshot_download("FunAudioLLM/SenseVoiceSmall")` 落到本地缓存**,
   以本地路径加载(`stt_model` 配置;`pipeline._resolve_stt_model`)。

| 交互 TTS(中文) | ⚠️ **无原生插件**:Pipecat TTS 插件表无 Qwen3-TTS/CosyVoice;**需薄胶水**——把 mlx-audio Qwen3-TTS 封装成 OpenAI 兼容 `/v1/audio/speech` 再接入;或接受 Kokoro(中文弱)/XTTS(CPML 非商用) | Pipecat 文档核实 |
| LLM | ✅ LM Studio 35B-A3B(OpenAI 兼容,Pipecat 直连) | 本机既有 |

**结论修正(相对 §9.1/9.2 初判)**:
1. WhisperLiveKit 成熟度**显著高于初判**(10.6K star、1 个开放 issue、日更)——作为字幕主框架的信心上调
2. Pipecat 中文 STT 插件核实存在但**非流式**(轮次级)→ 与 WhisperLiveKit 分工明确:交互轮次走 Pipecat,实时 partial 字幕走 WhisperLiveKit
3. **中文 TTS 是两框架共同的短板**(均无 Qwen3-TTS/CosyVoice 原生插件)→ 自封装 OpenAI 兼容 TTS 端点是必做胶水,不做重复造轮子
4. livekit/agents 中文本地模型无原生插件(云插件为主)→ 中文单机场景维持 Pipecat 优先
