## 3. 已修复的接线问题

后端 v1 `meeting_snapshot.payload.partial` 的契约是对象或 `null`：

```json
{
  "text": "正在确认",
  "speaker_key": "e1:s1",
  "speaker_name": "说话人 1"
}
```

前端仍将它声明为 `string | null`，并在 `meetingStore.applySnapshot` 中直接赋给
`partialText`。TypeScript 的断言没有拦截服务端真实 JSON；浏览器实测报错：

```text
Objects are not valid as a React child
```

页面 body 随后为空，无法完成会议录制页渲染。

已修复：

- `MeetingSnapshotPayload.partial` 已与 v1 schema 对齐为对象/null；
- `applySnapshot` 只将 `partial.text` 和 `partial.speaker_name` 写入渲染态，snapshot 清空时同步清除旧 speaker；
- sequence fixtures、store regression test 和浏览器回放均已更新；
- 后端 v1 schema 保持对象/null，不退回字符串。

## 4. 接线增强与剩余风险

1. mock 已补齐 `/api/services`、`/api/runtime` 和 loopback CORS；
2. `meetingApi`、服务健康探活、TTS 请求均统一经过 `apiUrl()`，控制/会议 WS 支持
   `VITE_MEETING_WS_URL`、`VITE_CONTROL_WS_URL`；
3. `ui/vite.config.ts` 支持 `VITE_DEV_PROXY_TARGET`，可将开发代理切换到 `8200` 或 LAN 后端；
4. `VITE_DATA_SOURCE` 已作为受控配置解析，但本次浏览器验收使用独立 HTTP/WS mock 服务，
   不把 in-process fixture/mock 注入作为生产运行路径；
5. 本次未执行真实录音结束、EOF/`input_audio_buffer.commit` → `session.completed`、PostgreSQL 故障恢复、权限和生产部署验收，
   这些仍由 Q1 目标环境完成。

## 6. 下一团队接线用法

### 6.1 通过开发代理

```bash
scripts/run-meeting-mock.sh --host 127.0.0.1 --port 8200
cd ui
VITE_DEV_PROXY_TARGET=http://127.0.0.1:8200 npm run dev -- --host 127.0.0.1 --port 5173
```

### 6.2 前端直连独立后端

`VITE_API_BASE_URL` 填后端 HTTP origin；如前后端不在同一 origin，同时显式填写两个
WebSocket 地址：

```bash
cd ui
VITE_API_BASE_URL=http://127.0.0.1:8200 \
VITE_MEETING_WS_URL='ws://127.0.0.1:8200/ws/v1/meetings?scenario=partial&delay_ms=100' \
VITE_CONTROL_WS_URL=ws://127.0.0.1:8200/ws/v1/control \
npm run dev -- --host 127.0.0.1 --port 5174
```

若只配置 `VITE_API_BASE_URL`，前端会从该 origin 推导 `ws://`/`wss://` 的默认 WS
地址；生产环境仍建议显式配置 WS 地址并由后端配置允许的前端 Origin。
