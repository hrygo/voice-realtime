# 会议助手前后端分离工作交接清单

> 文档状态：后端执行包、前端接线和联合验证记录已落盘，待双方正式签署
>
> 日期：2026-09-01
>
> 用途：将会议助手工作交接给不同的前端、后端、契约和 QA/发布团队，并让接收团队能够在不阅读对方内部实现的情况下开始工作。

## 1. 交接结论

后续采用五类工作包交接。当前 ASR/TTS 依赖由独立 SpeechRail 服务提供；交接只覆盖
`sona` 的应用协议和业务边界，不包含 SpeechRail 模型部署权限或 snapshot 路径。

```text
C0 公共契约与架构边界
        ├── B1 后端 producer
        ├── D1 独立联调环境
        └── Q1 集成、质量与发布
F1 前端 consumer（由前端团队独立实施）
```

本次后端执行顺序为 `C0 → B1 → D1 → Q1`；F1 由前端团队在 C0 评审通过后独立实施，随后再与 Q1 汇合。前端和后端不得以数据库表、Python 内部类、React store 结构或模型原始事件作为协作接口；所有跨团队依赖必须进入 `contracts/meeting-assistant/v1/`。

本次已完成 C0 公共契约、B1 后端 producer、D1 独立 mock/fixture 回放、F1 前端 consumer/UI
接线和 Q1 联合接线门禁；联合记录为 `Accepted with risks`，真实录音/EOF/权限/生产部署仍是
目标环境的后续验收项。接收团队应以实际工作树、测试输出和契约 fixture 为准，不以口头状态或
历史文档中的“已通过”描述为准。

## 3. 交接前必须说明的现状

### 3.1 已确认的架构事实

- PostgreSQL 保存会议元数据、confirmed 转录、说话人映射和 AI 纪要，是唯一事实源；
- 产品不保存会议音频；
- 会议期间仍由服务端控制音频所有权，语音助手、普通字幕和会议助手不能同时消费 PCM；
- 会议结束仍需 SpeechRail `commit` / `session.completed` EOF 冲刷，失败时进入明确的 interrupted/finalization timeout 语义；
- 说话人是会议内匿名 diarization，`speaker_key` 对前端保持不透明；
- SpeechRail `transcription.delta` partial 可丢失，`transcription.completed` 必须经过窗口对账和持久化；
- `meeting_snapshot` 是 WebSocket 重连基线，`resync_required` 必须回源 GET transcript；
- 阅读层可以派生合并，但不能覆盖事实层片段，也不能跨 `speaker_key` 或 `source_epoch` 合并。

### 3.2 交接时必须特别标注的未闭合项

| 项目 | 当前状态 | 接收团队要做的事 |
|---|---|---|
| `/api/runtime` 与 `/api/v1/runtime` | C0 已将 `/api/v1/runtime` 定为 canonical，旧路径仅保留兼容 | B1/F1 新代码只使用 canonical path |
| `start_subtitles` | C0 已纳入 AsyncAPI 命令枚举 | 接收团队在前端类型和联合测试中复核 |
| 事件 payload | C0 已为 9 类事件补独立 schema | 新增事件必须同步 schema、fixture 和变更日志 |
| snapshot 换会 | B1 已输出自洽 snapshot | F1 增加 reducer 测试并清理旧会议派生状态 |
| revision gap | 不连续版本不得静默拼接 | B1 已生产 `resync_required`，F1 严格回源 |
| `replace_from_ms` | 后端和前端边界条件需要统一 | C0 已固化 `<`/`>=` 规则并加测试 |
| partial speaker | 契约允许，但生产链路可能丢失 | B1 已保留显式已知 speaker，未知时保持 null |
| `raw_output` | 当前纪要 schema 可能暴露内部字段 | F1 不得依赖；C0 标记公共/内部边界 |
| 工作树基线 | 当前仓库可能存在未提交改动 | 交接单必须填写双方 commit SHA，不接收脏工作树作为发布基线 |

### 5.2 必须交付

- [ ] canonical URL、兼容 URL 和下线条件；
- [ ] 所有控制命令枚举，包括 `start_subtitles`；
- [ ] 所有会议事件的 payload schema；
- [ ] empty/active `meeting_snapshot` 的结构和生命周期；
- [ ] `event_id`、`occurred_at`、`runtime_revision`、`transcript_revision`、`content_revision` 的语义；
- [ ] `replace_from_ms` 精确边界规则；
- [ ] REST error envelope、HTTP 状态码和稳定错误码；
- [ ] 会议、转录片段、说话人、纪要的输入/输出字段表；
- [ ] partial、confirmed、revised 的状态和持久化边界；
- [ ] fixtures 的使用说明和失败样例；
- [ ] v1 additive 变更与 v2 breaking change 规则；
- [ ] 双方 reviewer、contract tag 和 changelog 流程。

### 5.3 验收条件

- [ ] 后端可以只根据契约生成并校验事件；
- [ ] 前端可以只使用 fixtures 渲染录制、历史、纪要和错误状态；
- [ ] fixture 不包含音频、令牌、完整环境变量或数据库连接信息；
- [ ] 前端不需要读取 Python、PostgreSQL 或 SpeechRail 内部类型；
- [ ] 删除或改变字段含义时能明确判断为 breaking change；
- [ ] 契约变更能够在 `CHANGELOG.md` 中追踪。

### 5.4 交接话术

交给后端团队：

> 你们是公共事件和 REST 资源的 producer。前端不依赖你们的内部对象；请以 v1 schema 和 fixture 为输出验收标准，并保证 revision、snapshot、resync 和错误码语义稳定。

交给前端团队：

> 你们是公共事件和 REST 资源的 consumer。可以在后端未启动时使用 fixture/mock 开发；请只依赖 schema 字段，不解析 `speaker_key`，不把阅读视图写回事实层。

## 8. Q1：QA、发布和回滚交接

### 8.1 接收范围

QA/发布团队负责验证 producer、consumer 和真实集成，不负责替代任一团队修复内部实现。

验证对象：

- 所有 `contracts/meeting-assistant/v1/` fixtures；
- REST API 和两个 `/ws/v1/*` channel；
- 前端 fixture/mock/backend 三种数据源；
- 会议切换、重连、断档、EOF、纪要完成和失败；
- 同版发布、兼容期和整体回滚。

### 8.2 测试矩阵

| 场景 | 后端验证 | 前端验证 | 集成判定 |
|---|---|---|---|
| 首次连接 | snapshot 结构和 meeting ID | 清理并建立本地状态 | 显示正确会议 |
| partial | payload 可选 speaker | 不计入 confirmed | 实时状态可解释 |
| confirmed | revision 和 replace window | 严格连续应用 | 无丢字/重复 |
| 会议切换 | 发送新 snapshot | 原子清空旧状态 | 无串会 |
| revision gap | 发送 resync_required | GET transcript | 最终与事实源一致 |
| WS 断线 | 可恢复/可重连 | 显示校准状态 | 不静默假同步 |
| speaker rename | content revision | 更新所有相关展示 | 不改 speaker key |
| EOF | `input_audio_buffer.commit` / `session.completed` / 超时语义 | finalizing/completed | 最终数据封存 |
| 纪要失败 | 稳定错误码 | 可重试/可解释 | 不丢已确认转录 |
| 长会议 | 分页/资源观测 | 虚拟化或窗口化 | 不因渲染崩溃 |

```text
VITE_DATA_SOURCE=fixture|mock|backend
```

前端必须可以在后端不可用时启动页面、加载 fixture、模拟延迟/乱序/断线/断档，并验证状态机结果。

### 9.3 环境限制

- 不把 PostgreSQL DSN、令牌、完整环境变量或模型 cache 路径放入交接包；
- 不要求前端团队启动真实 ASR 模型才能进行组件开发；
- 不使用生产数据库做联调；
- 不将 mock payload 放宽到与真实契约不一致；
- loopback/allowed Origin、`request_id` 和 WebSocket 关闭码规则保持可测试。

## 10. 第一次交接会议议程

按以下顺序完成一次 45–60 分钟交接：

1. **5 分钟：确认版本**
   - 填写 contract version、后端 SHA、前端 SHA、工作树状态。
2. **10 分钟：确认数据边界**
   - PostgreSQL 唯一事实源；不保存音频；匿名 speaker；前端不访问数据库。
3. **15 分钟：走一遍事件序列**
   - `meeting_snapshot → transcript_partial → transcript_reconciled → speaker_updated → resync_required → minutes_state_changed`。
4. **10 分钟：演示异常路径**
   - 会议切换、revision gap、WS 断线和 EOF。
5. **10 分钟：确认工作包和依赖**
   - C0 负责人、B1/F1 负责人、Q1 验收人和第一个交付日期。
6. **5 分钟：签署未闭合项**
   - 每一项必须有负责人、状态和下一步，不允许只写“后续关注”。

## 12. 交接完成标准

一次交接只有在以下条件全部满足时才能标记为 `Accepted`：

1. 接收团队可以从文档和公共契约定位所有工作入口；
2. C0 的路径、命令、事件、字段、错误码和 revision 规则没有未指派歧义；
3. 后端可以独立运行 producer contract tests；
4. 前端可以独立运行 fixture/mock consumer tests；
5. QA 可以使用同一批 fixtures 验证生产者和消费者；
6. 会议切换、断线、乱序、revision gap、resync 和 EOF 均有验收证据；
7. 现有未提交改动、已知风险和未完成项已经写入交接记录；
8. 双方知道什么可以修改、什么必须回到公共契约评审；
9. 发布和整体回滚步骤可以由非原作者执行。

## 13. 禁止的交接方式

- 只交一个前端页面截图，不交事件序列和错误路径；
- 只交数据库表结构，不交 HTTP/WS 公共契约；
- 只交后端接口地址，不交 schema、fixtures 和版本规则；
- 让前端直接读取 PostgreSQL 或导入后端 Python 类型；
- 让后端根据某个 React 组件的当前字段决定 API 结构；
- 以“模型输出看起来正常”替代 ASR、分人、分段和传输四类指标；
- 把未提交工作树、口头修复或历史测试结果当作发布基线；
- 将会议转录中的文本当作系统指令执行。
