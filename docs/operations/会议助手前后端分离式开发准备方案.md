# 会议助手前后端分离式开发准备方案

> 文档状态：C0/B1/D1/F1 接线已完成；Q1 联合验收为 `Accepted with risks`
>
> 日期：2026-09-01
>
> 目标：为前端团队和后端团队在不同节奏下并行开发、独立测试、独立联调和可控发布建立稳定边界。

> **SpeechRail 边界**：ASR、diarization profile 与 TTS 均由独立 SpeechRail 服务管理；本仓库的
> producer 只负责 Realtime v2 客户端适配、会议窗口/epoch 对账和应用协议，不下载或启动语音模型。

## 1. 决策摘要

采用“**契约优先、代码暂不拆仓、服务端权威、前端派生展示**”的分离路线：

1. 以 `contracts/meeting-assistant/v1/` 作为前后端公共契约的唯一事实源。
2. REST 使用 OpenAPI，WebSocket 使用 AsyncAPI，消息和资源使用 JSON Schema，所有关键状态配套 fixtures。
3. 后端团队负责领域状态、数据库、ASR/分人、窗口对账、事件语义和协议生产；前端团队负责协议消费、状态派生、交互和可视化。
4. 前端不读取数据库、不导入后端 Python 实现、不解析 `speaker_key` 的内部结构，也不把 UI 展示模型反写为后端事实。
5. 先在当前仓库按目录和 CI 边界分离；契约稳定后，再将 `contracts/` 发布为版本化制品或独立契约仓库。
6. 任何破坏性接口变更必须进入新的 major contract version；同一 major 内优先使用向后兼容的 additive 变更。

这份文档是团队协作和接口冻结的基线。本次已完成 C0 公共契约、B1 后端 producer、D1
独立 mock/fixture 回放、F1 前端 consumer/UI 接线和 Q1 联合接线门禁；真实录音、EOF
冲刷、权限及生产部署仍需在目标环境完成验收。

## 2. 为什么不立即拆成两个仓库

当前项目已经具备较清晰的模块边界和 `contracts/meeting-assistant/v1/` 目录，但协议、后端实现、前端消费和测试仍在同一工作树演进。立即拆仓会把尚未解决的契约漂移放大为跨仓库联调问题。

推荐顺序：

```text
当前单仓库
    ↓ 先冻结公共契约、补齐 fixtures 和契约测试
单仓库双团队并行
    ↓ 契约以 tag / artifact 发布，前后端只依赖公共制品
必要时再拆仓
```

不建议的两个替代方案：

- **立即拆仓**：隔离强，但会同时引入版本同步、私有包分发、联调环境和回滚协调成本；
- **共享后端生成的 TypeScript 内部类型**：短期方便，长期会让前端依赖后端目录结构和实现细节，不利于真正分离。

## 3. 当前基线与冻结前差距

### 3.1 已有资产

当前已有：

```text
contracts/meeting-assistant/v1/
├── openapi.json
├── asyncapi.yaml
├── schemas/
└── fixtures/
```

公共契约当前标称为 OpenAPI `3.1.0`、AsyncAPI `3.0.0`、`contract_version: "1"`，并已覆盖会议历史、会议详情、转录、说话人改名、纪要、导出、运行时状态和会议 WebSocket 事件。

现有运行手册已经规定：前端通过 HTTP 和 WebSocket 访问服务端，服务端是事实源；重连先消费 `meeting_snapshot`，收到 `resync_required` 或 revision 不连续时通过 HTTP 重建转录基线。

### 3.2 分离前必须完成的契约审计（执行前基线）

| 项目 | 当前观察 | 冻结前动作 |
|---|---|---|
| Runtime URL | OpenAPI 为 `/api/v1/runtime`，运行手册仍出现 `/api/runtime` | 将 `/api/v1/runtime` 定为 canonical；旧路径只作为有期限的兼容 alias |
| 控制命令 | 代码和测试已使用 `start_subtitles`，AsyncAPI 枚举尚未完全同步 | 同步 AsyncAPI、Schema、前端类型、后端校验和 fixtures |
| 事件 payload | `event-envelope.schema.json` 目前只约束为普通 object | 每种事件建立 payload schema，并用 discriminated union 校验 |
| RuntimeState | schema 允许 `additionalProperties: true` | 明确公共字段、内部字段和未知字段兼容策略 |
| Snapshot | 空闲态可能使用空 `meeting_id`，payload 内有独立 meeting 对象 | 明确空闲快照、活动快照和会议 ID 切换语义 |
| 错误 envelope | REST 已有统一雏形，但各路径状态码和错误码仍需逐项核对 | 固定 HTTP 状态、机器错误码、`request_id` 和 details 规则 |
| 纪要字段 | 当前 schema 暴露 `raw_output`，前端不应依赖内部原始模型输出 | 标记为内部候选字段；v1 保持兼容，后续版本明确移除或隔离 |
| Revision | 已有 `transcript_revision`、`content_revision`、`runtime_revision` | 为每种 revision 写出所有权、递增规则、乱序和恢复规则 |

冻结前必须以“代码、契约、fixtures、测试、运行手册”五方一致为准，不能只修改 TypeScript 类型或 Markdown 说明。

## 4. 目标职责边界

### 4.1 后端团队负责

- `src/voice_realtime/meeting/` 领域服务、Repository、恢复 journal、纪要任务；
- `src/voice_realtime/ui/subtitle_proxy.py` SpeechRail Realtime v2 连接、事件规范化、EOF 和重连；
- `src/voice_realtime/ui/` 运行时控制、会议事件网关和服务端权威状态；
- PostgreSQL schema、migration、事务、唯一事实源和数据恢复；
- SpeechRail ASR/diarization、说话人平滑、窗口对账和确认片段语义；
- REST/WS 协议的生产端实现、错误码和服务端日志；
- OpenAPI/AsyncAPI/JSON Schema 的语义维护，并提供可消费 fixtures。

后端不得把数据库表结构、内部异常、模型原始输出、SpeechRail 私有对象或 Python 类型直接当作前端接口。

### 4.2 前端团队负责

- `ui/src/contracts/` 公共类型适配和运行时边界校验；
- `ui/src/services/` HTTP 客户端、错误映射和请求取消；
- `ui/src/hooks/` WebSocket 生命周期、重连和事件消费；
- `ui/src/stores/` 服务端快照、revision、partial、confirmed 和 UI 派生状态；
- `ui/src/components/` 录制页、历史页、纪要页、阅读视图和可访问性；
- 只依赖公共契约和 fixtures 的单元测试、组件测试和 Mock 联调；
- 用户可见文案、加载/错误/重同步状态和交互行为。

前端不得读取 PostgreSQL，不得依赖后端模块导入路径，不得根据 `speaker_key` 的字符串格式推断 epoch 或真实身份，不得把阅读层合并结果作为事实层数据提交。

### 4.3 共同负责

- `contracts/meeting-assistant/v1/`；
- breaking change 评审和版本发布；
- fixtures 的业务真实性；
- 契约验证、生产者测试、消费者测试和跨团队验收；
- 安全、隐私、错误码、兼容期和回滚方案。

公共契约变更至少需要前端、后端各一名 reviewer；没有双方认可的 fixture 和兼容说明，不得合并。

## 5. 公共契约分层

### 5.1 协议层

协议层只描述传输和生命周期，不泄露实现：

- HTTP：方法、路径、查询参数、请求体、响应体、状态码；
- WebSocket：channel、连接方向、消息 envelope、心跳、关闭码和重连规则；
- JSON Schema：字段类型、必填字段、枚举、null 语义、长度和格式；
- fixtures：正常、空闲、失败、断档、重连、partial、confirmed 和完成态样例。

### 5.2 领域层

领域层描述会议、转录、说话人、纪要和运行时状态：

- `meeting_id` 是会议资源的唯一 ID；
- `speaker_key` 是不透明的会议内标识，前端只能原样保存和回传；
- `source_epoch` 用于隔离不同 ASR 会话时间线，不能由前端自行合并；
- `transcript_revision` 表示确认转录的对账版本；
- `content_revision` 表示说话人改名或内容变化影响的纪要基线；
- `runtime_revision` 表示运行时工作负载和 PCM owner 的权威状态版本；
- 时间字段统一使用 ISO 8601 UTC，片段时间使用非负整数毫秒。

### 5.3 展示层

展示层是前端派生模型，不作为后端公共事实：

```text
TranscriptSegment  →  TranscriptViewBlock  →  UI Card
```

`TranscriptViewBlock` 可以包含多个 `segment_ids`，但不能跨 `speaker_key` 或 `source_epoch` 合并。时序视图使用 `TranscriptSegment`，阅读视图使用 `TranscriptViewBlock`，纪要使用最终确认内容和 evidence segment IDs。

## 6. REST API 约定

### 6.1 当前公共资源

以下路径以 `/api/v1` 为公共基线：

| 方法 | 路径 | 责任 |
|---|---|---|
| GET | `/api/v1/runtime` | 获取服务端权威运行时状态 |
| GET | `/api/v1/meetings` | 游标分页获取会议历史 |
| GET | `/api/v1/meetings/{meeting_id}` | 获取会议详情 |
| PATCH | `/api/v1/meetings/{meeting_id}` | 更新会议标题 |
| DELETE | `/api/v1/meetings/{meeting_id}` | 删除会议，需遵守显式确认和冲突规则 |
| POST | `/api/v1/meetings/{meeting_id}/generate-title` | 生成并更新会议标题 |
| GET | `/api/v1/meetings/{meeting_id}/transcript` | 获取完整确认转录基线 |
| PATCH | `/api/v1/meetings/{meeting_id}/speakers/{speaker_key}` | 更新会议内说话人显示名 |
| POST | `/api/v1/meetings/{meeting_id}/minutes` | 创建纪要版本，支持 `Idempotency-Key` |
| GET | `/api/v1/meetings/{meeting_id}/minutes/{version}` | 获取指定纪要版本 |
| GET | `/api/v1/meetings/{meeting_id}/export` | 导出 `md/txt/srt/json` |

列表接口必须支持游标分页，前端不得假设会议历史一次性返回全部数据。

### 6.2 请求和响应原则

- 请求和响应字段使用 camelCase 或现有契约约定，不在同一版本混用命名风格；
- 输入和输出模型分离，服务端生成的 ID、时间、revision 不能由前端伪造；
- 新字段优先 optional/additive；
- 新枚举值出现时，前端必须有未知值兜底，不能因 exhaustive switch 崩溃；
- 第三方或模型输出进入 HTTP 响应前必须由服务端校验和清洗；
- `raw_output` 等内部诊断字段不得成为前端功能依赖。

### 6.3 统一错误 envelope

所有 REST 错误采用同一结构：

```json
{
  "error": {
    "code": "REVISION_CONFLICT",
    "message": "会议转录版本已变化，请重新加载。",
    "request_id": "request-uuid",
    "details": {
      "expected_revision": 4,
      "actual_revision": 5
    }
  }
}
```

约定：

| HTTP | 含义 |
|---|---|
| 400 | 请求格式或参数结构错误 |
| 404 | 资源不存在 |
| 409 | 资源版本、状态或幂等冲突 |
| 422 | 结构合法但业务校验失败 |
| 503 | 依赖服务或持久化暂不可用 |

`message` 供用户展示但不能作为程序分支条件；前端只依赖稳定的 `error.code`。

## 7. WebSocket 约定

### 7.1 Channel 责任

| Channel | 方向 | 作用 | 是否改变状态 |
|---|---|---|---|
| `/ws/v1/control` | 双向 | 运行时控制命令和 ack | 是 |
| `/ws/v1/meetings` | 服务端 → 前端 | 当前会议事件和快照 | 否，前端只消费 |
| `/ws/assistant/cmd` | 双向 | 兼容旧助手控制协议 | 仅兼容期保留 |
| `/ws/subtitles` | 服务端 → 前端 | 只读字幕兼容通道 | 不得隐式抢占模式 |

新功能优先使用 `/ws/v1/*`；兼容路径必须注明保留版本和下线条件。

### 7.2 事件 envelope

公共事件固定包含：

```json
{
  "contract_version": "1",
  "type": "transcript_reconciled",
  "event_id": "event-uuid",
  "meeting_id": "meeting-uuid",
  "occurred_at": "2026-08-26T08:00:00Z",
  "payload": {}
}
```

语义约定：

- `event_id` 用于去重，不能用作顺序判断；
- `occurred_at` 用于记录和展示，不能替代 revision；
- durable 转录顺序由 `transcript_revision` 决定；
- 运行时状态顺序由 `runtime_revision` 决定；
- 同一会议的 speaker/纪要内容变化由 `content_revision` 决定；
- `meeting_snapshot` 是连接、重连和基线恢复入口；
- `transcript_partial` 是易失展示事件，不计入确认转录事实；
- `transcript_reconciled` 携带 `replace_from_ms` 和确认片段窗口；
- `resync_required` 表示客户端不能自行猜测缺失内容，必须回源 GET transcript；
- 事件 payload 必须按 `type` 做 JSON Schema 校验，禁止所有事件共用一个宽泛 object。

### 7.3 前端事件消费状态机

```text
connect
  ↓
meeting_snapshot
  ↓
校验 meeting_id / revision
  ├── transcript_partial       → 更新单一 partial 展示区
  ├── transcript_reconciled   → 连续 revision 才应用
  ├── speaker_updated          → 更新 speaker 显示名和 contentRevision
  ├── meeting_state_changed    → 更新 recording/finalizing/completed/interrupted
  ├── minutes_state_changed    → 更新纪要任务状态
  ├── health_changed           → 更新可观察健康状态
  ├── transcription_gap        → 显示可操作的缺口提示
  └── resync_required           → GET transcript，完成后恢复消费
```

当 snapshot 的会议 ID 变化时，前端必须原子清理上一场会议的 `segments`、`speakers`、`minutes`、`gaps` 和 partial；异步 HTTP 回写必须再次校验目标会议 ID。

### 8.1 目录约定

`contracts/meeting-assistant/v1/README.md` 应说明：版本、维护人、canonical URL、事件顺序、错误码、兼容策略、fixture 用法和变更流程。

### 8.2 版本规则

- `contract_version` 只表示 major contract version，当前为字符串 `"1"`；
- OpenAPI/AsyncAPI 的 `info.version` 使用完整 semver，例如 `1.0.0`；
- `1.x` 只做向后兼容变更：新增 optional 字段、增加 fixture、增加非破坏性 endpoint；
- 删除字段、修改字段类型、改变 null 语义、改变 revision 规则、改变事件必填字段，进入 `v2`；
- breaking change 必须同时提供迁移说明、双端适配窗口和回滚方案；
- 前端必须忽略未知事件或未知 optional 字段，并提供可观察的降级状态；
- 后端在兼容期内可以生产旧字段，但不得同时改变同一字段含义。

### 8.3 变更流程

```text
提出契约变更
    ↓
判断 additive / breaking
    ↓
更新 schema、OpenAPI/AsyncAPI、fixtures、CHANGELOG
    ↓
后端 producer contract test
    ↓
前端 consumer contract test
    ↓
双方 review + 集成联调
    ↓
发布 contract artifact / tag
```

任何未进入 `contracts/` 的临时字段都不得用于跨团队功能依赖。

## 9. 独立开发和联调环境

### 9.1 后端团队

后端本地需要提供：

- HTTP API：`http://127.0.0.1:8100/api/v1`；
- Runtime：`http://127.0.0.1:8100/api/v1/runtime`；
- Control WS：`ws://127.0.0.1:8100/ws/v1/control`；
- Meeting Event WS：`ws://127.0.0.1:8100/ws/v1/meetings`；
- 可重复的临时 PostgreSQL schema；
- 由 fixtures 驱动的事件回放或测试模式；
- 脱敏的 request/event/revision 诊断日志。

后端联调环境不能要求前端连接数据库、读取本地 runtime 文件或启动 SpeechRail 才能验证基本应用协议；真实音频验收另行执行。

### 9.2 前端团队

前端至少支持三种数据源：

1. `fixture`：纯本地静态事件和 REST 响应；
2. `mock`：模拟延迟、乱序、断线、重复、revision gap 和错误；
3. `backend`：连接真实本地后端。

建议约定以下前端配置名，实际接入时保持单一命名：

```text
VITE_API_BASE_URL
VITE_MEETING_WS_URL
VITE_CONTROL_WS_URL
VITE_DATA_SOURCE=fixture|mock|backend
```

fixture/mock 必须与真实 v1 schema 校验，不能另造一套“为了方便而更宽松”的类型。

### 9.3 联调环境的最低能力

- 可通过一条命令启动 mock 和前端；
- 可选择单个 fixture 或按时间回放一组事件；
- 可注入 `transcript_revision` 断档；
- 可注入不同 `meeting_id` 的 snapshot；
- 可注入 `resync_required`、HTTP 404/409/503；
- 可验证前端最终状态与 fixture 中的 authoritative snapshot 一致。

## 10. 两团队并行工作包

### 10.1 共享契约工作包 C0

- 完成路径、命令、事件、错误码和字段的差异审计；
- 将每种事件拆成独立 JSON Schema；
- 补齐 `start_subtitles`、partial speaker、snapshot、gap、resync fixtures；
- 统一 REST/WS error envelope；
- 固化 revision 和 `replace_from_ms` 语义；
- 发布 `v1.0.0` 基线和变更日志；
- 由双方各自接入同一批 fixtures。

### 10.2 后端工作包 B1

- 实现会议 ID、revision、窗口替换和重连恢复的权威行为；
- 将 partial speaker 在可确定时传递，不确定时保持 null；
- 对所有公共 HTTP/WS 输出执行 schema 校验；
- 提供稳定错误码和 `request_id` 关联；
- 增加 producer contract tests；
- 提供不依赖真实模型的事件回放和故障注入入口；
- 保持 PostgreSQL 唯一事实源和不保存音频的边界。

### 10.3 前端工作包 F1

- 使用公共 schema/fixtures 形成协议适配层；
- 严格处理 snapshot、revision gap、过期事件和 resync；
- 将 confirmed segment 与 partial 分开；
- 从 canonical segments 派生阅读块，不跨说话人或 epoch 合并；
- 增加时序视图/阅读视图、匿名说话人显示和可访问交互；
- 所有 API 错误按 `error.code` 映射文案；
- 使用 fixture/mock 完成无后端组件测试和消费者契约测试。

### 10.4 集成工作包 Q1

- 运行 producer/consumer contract tests；
- 验证真实后端和 mock 的同一 fixture 行为；
- 验证同版发布、旧前端兼容和整体验证回滚；
- 验证断线、重连、会议切换、EOF 和纪要完成路径；
- 输出带前后端 commit SHA、contract version 和环境信息的联调记录。

任务依赖关系：本次后端执行采用 `C0 → B1 → D1 → Q1`；F1 由前端团队在 C0 fixtures 稳定后独立实施，随后与 Q1 汇合。前端视觉和阅读层不需要等待后端所有 ASR 模型调优完成。

## 11. 与实时转录优化方案的映射

此前的实时转录优化方案拆分为以下跨团队交付：

| 优化项 | 后端交付 | 前端交付 | 共享验收 |
|---|---|---|---|
| 会议切换清理 | snapshot 语义和目标会议 ID | reducer 原子 reset | 新旧会议无串数据 |
| revision 对账 | 递增、replace window、resync 事件 | 连续性判断和 HTTP 回源 | 乱序/断档无丢字重复 |
| partial/confirmed | partial speaker、confirmed window | 状态展示和单一 partial 区 | confirmed 数量准确 |
| 阅读视图 | 提供稳定 segment/evidence ID | 派生 `TranscriptViewBlock` | 不跨 speaker/epoch 合并 |
| 领域术语 | 接收并记录会议级术语上下文 | 术语输入和结果标记 | 术语 exact match 评测 |
| 说话人体验 | speaker mapping 和改名事件 | 颜色、匿名文案、重命名 | 会议内稳定且可解释 |
| 可访问性 | 提供稳定状态和错误码 | button、focus、status、键盘 | 辅助技术和键盘验收 |

详细问题和 ASR/分段调优方法见 [`会议助手实时转录体验优化方案.md`](../solutions/会议助手实时转录体验优化方案.md)。

## 12. 安全、隐私与数据边界

- 转录文本是用户内容，前端按纯文本或经过清洗的 Markdown 渲染，不能把文本中的命令当作 UI 指令；
- 前端不得将 `speaker_key`、数据库 ID 规则或内部错误堆栈展示为身份信息；
- 不把音频、完整环境变量、令牌或数据库连接信息放入 fixtures、日志或公共契约；
- `raw_output`、模型内部诊断和 SpeechRail 私有事件不是前端公共依赖；
- WebSocket 仍执行 loopback/allowed Origin 和 request_id 校验；
- 会议删除、纪要重生成和 speaker 改名的权限与冲突语义由后端控制；
- 前端缓存只作为临时展示缓存，不能取代 PostgreSQL 或服务端 snapshot。

## 13. 发布、回滚和废弃策略

### 发布

发布单必须记录：

- `contract_version` 和 artifact/tag；
- 后端 commit SHA；
- 前端 commit SHA；
- OpenAPI/AsyncAPI/schema 校验结果；
- producer/consumer contract test 结果；
- 真实联调环境和配置版本。

### 回滚

- v1 阶段前后端仍按同一发布单整体回滚；
- 不能只回滚前端而保留不兼容的事件生产者；
- 不能只回滚后端而让前端继续依赖新字段；
- 数据库 migration 和公共契约必须分别记录可回滚性；
- 回滚不得删除会议、confirmed 转录、recovery journal 或纪要事实。

### 废弃

废弃接口至少经历：

```text
标记 deprecated
    ↓
文档和日志提示替代路径
    ↓
兼容期内保留并测试
    ↓
新 major version 移除
```

## 14. 分离前完成标准

只有满足以下条件，才建议将两个团队移入长期独立节奏：

1. `contracts/meeting-assistant/v1/` 有 README、CHANGELOG、OpenAPI、AsyncAPI、独立事件 schema 和完整 fixtures；
2. canonical URL、控制命令、事件 payload、错误码和 revision 规则没有未记录的歧义；
3. 后端可以脱离前端通过 producer contract tests 验证；
4. 前端可以只使用 fixtures/mock 完成主要页面和状态机测试；
5. 前端不导入后端 Python/数据库/内部运行时模块；
6. 会议切换、断线、乱序、revision gap、resync、EOF 和纪要状态均有跨团队测试；
7. 旧客户端兼容策略和 v2 breaking change 规则已写入文档；
8. 一次完整联调可以复现、记录和回滚；
9. 两个团队分别拥有明确的目录、reviewer 和发布责任人。

## 15. 首批执行顺序

### 第 1 批：契约冻结准备

- [ ] 审计 `/api/runtime` 与 `/api/v1/runtime`，确定 canonical path；
- [ ] 同步 `start_subtitles` 到 AsyncAPI、Schema、类型和 fixtures；
- [ ] 拆分事件 payload schema；
- [ ] 补充契约 README、CHANGELOG 和版本规则；
- [ ] 形成 `v1.0.0` 公共基线。

### 第 2 批：后端 producer 可测

- [ ] 后端完成 producer contract tests 和事件回放；
- [ ] 提供不依赖 PostgreSQL、ASR、TTS 的 `vr-meeting-mock` fixture/mock 服务；
- [ ] 后端验证错误、断档、重连、snapshot 和版本兼容；
- [ ] 建立共享联调记录模板。

前端团队可使用以下独立入口开展 F1：

```bash
scripts/run-meeting-mock.sh
```

默认地址为 `http://127.0.0.1:8200`；会议事件可通过
`/ws/v1/meetings?scenario=happy_path|partial|revision_gap|meeting_switch|disconnect|error`
回放，并用 `delay_ms`、`duplicate`、`disconnect_after` 注入确定性网络场景。

### 第 3 批：转录体验优化并行实施

- [ ] 后端修复状态一致性、partial speaker 和窗口边界；
- [ ] 前端实现状态表达、阅读视图、speaker 视觉和可访问性；
- [ ] 共同完成 ASR/分人/分段评测；
- [ ] 以统一 contract version 发布。

### 第 4 批：评估是否拆仓

- [ ] 连续两个版本完成同一套契约和回滚门禁；
- [ ] 前后端均能在对方不可用时使用 mock/fixture 开发；
- [ ] 公共契约已经可以作为独立 artifact 发布；
- [ ] 再评估拆仓收益是否超过发布和运维成本。
