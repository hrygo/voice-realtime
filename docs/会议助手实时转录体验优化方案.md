# 会议助手实时转录体验优化方案

> 文档状态：方案与后端执行基线；前端阅读体验实现待 F1 团队完成
>
> 日期：2026-08-26
>
> 适用范围：会议助手实时录音页、WhisperLiveKit 转录事件、Sortformer 说话人分离、前端 transcript reducer、阅读视图与质量评测。

## 1. 文档目的

本方案把会议助手实时转录界面暴露出的体验和链路问题整理为可实施的优化计划，重点解决：

- 实时 ASR 的确认、修订和暂存状态不够清晰；
- ASR 确认片段、说话人轮次与用户阅读段落概念混淆；
- 会议切换、事件乱序、revision 断档时可能出现的状态不一致；
- 匿名说话人、短插话和跨说话人接话造成的误判；
- 业务专有名词识别质量和可验证性不足；
- 重点标记、复制、键盘操作和动态状态播报不够完善。

本方案不改变以下既定边界：

- PostgreSQL 是会议元数据、确认转录、说话人映射和纪要的唯一事实源；
- 产品不保存会议音频；
- `speaker_key` 对前端保持不透明，匿名说话人不能被推断为真实身份；
- 会议结束仍需经过 EOF 冲刷和 `ready_to_stop` 优雅收尾；
- 语音助手、普通字幕和会议助手仍遵守运行时音频所有权互斥。

## 2. 结论摘要

当前系统的主要矛盾不是单一 CSS 或模型参数问题，而是三个层级被直接串联：

```text
ASR 确认片段  →  说话人轮次  →  用户阅读段落
```

截图中的“已记录 6 个段落”实际更接近“6 个已确认发言片段”。`Backfill`、`image` 和“并补齐本地缓存”可能是实际的短插话或说话人切换，不能仅凭截图认定为错误；但把它们直接以机器片段形式展示，确实降低了可读性和用户对结果的信任。

建议按以下优先级推进：

1. **先修数据正确性**：会议切换清理、revision 连续性、重连和窗口替换边界。
2. **再修语义表达**：区分 `partial`、`confirmed`、`revised`，把“段落”改成“发言片段”。
3. **增加双视图**：保留可审计的时序视图，同时提供不跨说话人的阅读视图。
4. **最后调 ASR/分人参数**：基于真实语料、术语集和可量化指标调参，不凭单张截图改模型。

## 3. 当前证据与边界

### 3.1 截图直接观察

截图显示：

- 当前会议录制中，计时约两分钟；
- 界面显示“已记录 6 个段落”；
- 每条卡片包含匿名说话人、时间范围、转录文本和“标为重点”；
- 同一说话人有多个相邻或间隔较大的卡片；
- `01:33–01:38` 出现 `说话人 2 → 说话人 1 → 说话人 2` 的快速交替；
- 文本包含 `Email Agent`、`Comail`、`Backfill`、`image`、`ZMYL` 等可能的业务术语。

截图无法单独证明以下事项：

- 具体文字是否识别错误；
- `Backfill` 是否为真实的第二位说话人插话；
- “说话人 1/2”是否被错误分配；
- 文本是否曾经经历了 partial 到 confirmed 的修订；
- 是否发生过丢事件、重复事件或重连。

这些问题必须使用原始音频、WLK 事件、数据库确认结果和事件日志验证。

### 3.2 执行前代码事实

当前录制页基本按一条 `TranscriptSegment` 渲染一张卡片，并使用 `segments.length` 显示“段落”数量，见 [`MeetingRecordingView.tsx`](../ui/src/components/meeting/MeetingRecordingView.tsx)。历史页已经存在说话人统计和颜色，但录制页没有完全复用同一套说话人视觉编码，见 [`MeetingTranscriptViewer.tsx`](../ui/src/components/meeting/MeetingTranscriptViewer.tsx)。

后端已经具备窗口对账、`transcript_revision`、`source_epoch` 和说话人平滑机制：

- [`MeetingSession._on_window`](../src/voice_realtime/meeting/session.py) 对确认窗口持久化后发出 `transcript_reconciled`；
- [`DiarizationSmoother`](../src/voice_realtime/meeting/diarization_smoother.py) 当前使用 `min_duration_ms=350` 和 `hangover_gap_ms=800`，并只对特定短暂 A-B-A 抖动做修正；
- [`TranscriptNormalizer`](../src/voice_realtime/asr/adapters/wlk.py) 按 `source_epoch`、说话人、时间和文本生成标准片段；
- [`SubtitleSettings`](../src/voice_realtime/config.py) 当前使用 2 秒 chunk、12 秒左上下文、640ms 右上下文、6 个 hold-back words 和 2 次稳定迭代。

需要重点修正的状态风险：

- [`meetingStore.applySnapshot`](../ui/src/stores/meetingStore.ts) 在会议 ID 改变时没有同步清理所有旧的转录、说话人、纪要和 gap 状态；
- [`useMeetingSocket`](../ui/src/hooks/useMeetingSocket.ts) 当前只在 revision 跳跃超过 10 时主动基线同步，不能覆盖较小但仍不连续的断档；
- partial 事件虽然允许携带说话人，但 [`MeetingSession._on_window`](../src/voice_realtime/meeting/session.py) 当前将 partial 的说话人字段置空；
- 后端窗口替换使用 `end_ms >= replace_from_ms`，前端稳定历史筛选使用 `end_ms <= replaceFromMs`，精确边界规则需要统一。

### 3.3 本次后端执行结果

- 后端 `MeetingEventBroadcaster` 已对同一会议的 durable revision 做连续性门禁；过期事件丢弃，断档转为
  `resync_required`，快照恢复后重新建立 revision 基线；
- `TranscriptWindow`、`MeetingSession` 和会议快照已保留显式 partial speaker；未知或无法解释的 speaker
  不推断展示名称，保持 `null`；
- PostgreSQL 对账边界统一为保留 `end_ms < replace_from_ms`，替换 `end_ms >= replace_from_ms` 的窗口，
  且有精确边界回归测试；
- F1 中的 snapshot 换会清理、严格 consumer 回源、时序/阅读双视图和可访问性仍由前端团队实现；
- 可用 `scripts/run-meeting-mock.sh` 在无真实模型和数据库时回放上述协议场景。

## 4. 问题分级

| 优先级 | 问题 | 用户影响 | 处理原则 |
|---|---|---|---|
| P0 | 会议切换后旧状态残留 | 可能看到上一场会议的文本、说话人或纪要 | 先清空旧状态，再装载新快照 |
| P0 | revision 断档或乱序处理不完整 | 可能漏字、重复、显示非最新文本 | 严格按会议 ID 和 revision 对账，必要时拉取基线 |
| P1 | 将机器片段称为“段落” | 用户以为系统错误切句 | 改用“已确认发言片段”，增加阅读视图 |
| P1 | partial/confirmed/revised 边界模糊 | 用户不知道哪些文字还会变化 | 明确状态，稳定尾部再进入确认列表 |
| P1 | 匿名说话人缺少解释和稳定视觉编码 | 用户误以为系统识别了真实身份或分人失效 | 使用“匿名说话人”、颜色、重命名和待确认状态 |
| P1 | 领域术语可能识别错 | 会议结论和纪要中的产品名、缩写失真 | 会议级术语表加金标准评测 |
| P2 | 小按钮和卡片交互不够可访问 | 键盘用户、低视力用户和触控用户操作困难 | 原生按钮、状态语义、可见 focus、足够点击区域 |
| P2 | 长会议卡片持续增长 | 滚动、渲染和查找体验下降 | 虚拟化、分页或按时间窗口加载 |

## 5. 目标架构

### 5.1 事实层与展示层分离

采用“一个事实层、多个派生视图”的结构：

```text
WLK / Diarization Events
          ↓
事件去重、版本校验、窗口对账
          ↓
Canonical Transcript Segments
          ├── 时序视图：逐片段展示，可审计
          ├── 阅读视图：派生自然段，不跨说话人
          └── AI 纪要：仅使用最终确认内容
```

事实层保留原始确认粒度，不用阅读层的合并结果覆盖事实层。建议将阅读块定义为派生对象：

```text
TranscriptSegment
  id, order, source_epoch, speaker_key
  start_ms, end_ms, text
  status: partial | confirmed | revised
  transcript_revision

TranscriptViewBlock
  block_id
  segment_ids
  source_epoch, speaker_key
  start_ms, end_ms, text
```

`stability` 或置信度只有在模型定义清晰并完成校准后才添加，不能把“模型暂时不改”当作“识别正确”。

### 5.2 事件一致性规则

在当前每次窗口对账使 `transcript_revision` 单调递增 1 的契约下，前端 reducer 应遵循：

1. `meeting_snapshot.meeting.id` 与当前会议不同：原子清理旧的 `segments`、`speakers`、`minutes`、`gaps` 和 partial，再装载新快照。
2. 事件会议 ID 不是当前会议：丢弃，除非它属于明确的历史详情加载流程。
3. 事件 revision 小于等于当前 revision：视为过期事件，不覆盖当前状态。
4. 事件 revision 不是 `current + 1`：进入“正在校准”，通过 HTTP 获取完整 transcript 基线。
5. 收到 `resync_required`：无条件基线同步，不尝试局部猜测。
6. `replace_from_ms` 统一为：保留 `end_ms < replace_from_ms` 的稳定历史，替换 `end_ms >= replace_from_ms` 的窗口内容。
7. 基线同步期间保留已知的稳定历史，但不能继续把未知 revision 的事件拼到当前列表。

服务端仍是事实源，前端只负责可取消的派生状态。重连、浏览器刷新和多客户端连接都必须收敛到服务端最新快照。

### 5.3 partial 与 confirmed

实时界面只保留一个位于列表末尾的 partial 区域：

- partial 文本可以被替换，不计入“已确认片段”数量；
- confirmed 文本进入稳定列表后不因普通重绘闪烁；
- partial 能确定说话人时显示对应匿名说话人；
- 分人尚未完成时显示“说话人待确认”，不猜测；
- 发生修订时更新原片段或窗口，不重复创建卡片。

行业流式转录接口普遍将 interim/partial 与 final/confirmed 分开，并允许确认前修订；AWS 还特别提示稳定化会在延迟与准确率之间产生权衡，Google 的 `stability` 表示结果改变的可能性，不等于正确率。[AWS Streaming Partial Results](https://docs.aws.amazon.com/transcribe/latest/dg/streaming-partial-results.html)、[Google StreamingRecognitionResult](https://docs.cloud.google.com/speech-to-text/docs/reference/rest/v2/StreamingRecognitionResult)

## 6. 前端体验方案

### 6.1 文案和状态

将：

```text
已记录 6 个段落
```

改为：

```text
已确认 6 个发言片段 · 2 位匿名说话人 · 正在识别
```

建议增加以下状态：

- `录制中`
- `正在识别`
- `正在校准转录`
- `连接中断，已暂停接收`
- `连接已恢复，正在补齐`
- `正在结束会议并冲刷最后语音`

界面中应明确显示会议助手不会对录音内容进行语音回复，避免用户把“录制中”和“语音助手正在监听”混淆。

### 6.2 时序视图和阅读视图

提供两个切换视图：

#### 时序视图

目标是审计和定位：

- 一条确认片段一张卡片；
- 保留原始时间戳和 `segment_id`；
- 不做跨片段语义合并；
- 适合排查 ASR、分人和重连问题。

#### 阅读视图

目标是快速理解会议内容。仅在以下条件同时满足时合并：

- `speaker_key` 相同；
- `source_epoch` 相同；
- 中间停顿不超过可配置阈值；
- 没有明确说话人切换；
- 合并后未超过最大时长和最大字数。

建议初始候选参数为 `gap <= 1200ms`、单块最多 15 秒或 180 个中文字符，之后用真实会议语料调优。这些参数只属于阅读层，不应直接改变数据库事实层。

永远不能跨说话人合并。截图中的：

```text
S1  Email Agent 产品手册……
S2  Backfill
S1  image，即可批量抓取……
S2  并补齐本地缓存。
```

即使阅读上看起来像一句完整方案，也应在时序视图中保留四个发言片段；只有确认录音后，才可以在纪要层做语义归纳。

### 6.3 说话人显示

- 使用“匿名说话人 1”而不是让用户误以为是真实身份；
- 录制页与历史页复用同一个 meeting-scoped speaker color mapping；
- 颜色不能作为唯一编码，必须同时显示文字；
- speaker label 旁显示“可重命名”而非“已识别”；
- 说话人数量来自当前有效 speaker labels，不把 `sortformer-max-speakers=4` 当成模型实际识别出的 4 人；
- 超过上限时显示“可能存在未区分的额外说话人”，不要静默覆盖。

Streaming Sortformer 研究使用说话人缓存和动态嵌入来降低低延迟分人中的标签不稳定；WhisperLiveKit 文档也明确 `--sortformer-max-speakers` 是上限而不是实际人数，标签按到达顺序保留。[Streaming Sortformer 论文](https://arxiv.org/abs/2507.18446)、[WhisperLiveKit 官方 README](https://github.com/QUENTINFUXA/WHISPERLIVEKIT)

### 6.4 操作与可访问性

- 卡片选择使用真实按钮或明确的可选择列表语义，不让普通 `<div>` 独自承担键盘交互；
- “标为重点”使用 `aria-pressed` 表示开关状态；
- 复制操作提供可访问名称和成功状态；
- partial 和“正在校准”等状态放入 `role="status"` / `aria-live="polite"` 区域，但不要把每个转录字符都作为高频播报；
- 所有控件有可见 focus，颜色对比度满足 WCAG；
- 小图标点击区域至少达到 WCAG 2.2 AA 的 24×24 CSS px，桌面端建议使用 32px 或更大；
- 键盘快捷键 `S` 需要在页面中可发现，并避免输入框聚焦时误触发。

W3C 的 ARIA Button Pattern 建议使用原生按钮和正确的键盘行为，并用 `aria-pressed` 表示 toggle button 状态；WCAG 也要求动态状态变化在不移动焦点的情况下可被辅助技术识别。[WAI-ARIA Button Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/)、[WCAG Status Messages](https://www.w3.org/WAI/WCAG21/Understanding/status-messages.html)

## 7. ASR、分段与领域术语方案

### 7.1 不从单张截图直接改分段参数

当前 `DiarizationSmoother` 的行为是：

- 过短且无实际文字的噪声片段可被过滤；
- 小于 350ms 的 A-B-A 中间抖动可被修正；
- 同一说话人在 800ms 内的相邻片段可以合并；
- 有意义的短文本不会仅因时长短而被删除。

因此，`Backfill` 这样的单词片段可能是合法的快速接话。优化时应将“说话人纠错”和“阅读层合并”分离，并通过语料比较以下参数组合：

- `min_duration_ms`：250 / 350 / 500；
- `hangover_gap_ms`：400 / 800 / 1200；
- WLK `hold_back_words`：4 / 6 / 8；
- WLK `stable_iterations`：1 / 2。

每次只改变一组因素，记录 ASR、分人、边界和确认延迟变化。

### 7.2 会议级术语表

在会议开始前或录制页中提供可选的术语表，初始覆盖：

```text
Email Agent
Comail
Backfill
ZMYL
image
本地缓存
内嵌截图
批量抓取
```

术语表只作为识别上下文提示，不应无条件替换识别结果。对于不确定词，界面允许用户在确认后加入术语表，避免把 ASR 猜测固化为事实。

每个术语至少测试：

1. 不提供术语表；
2. 提供术语表；
3. 提供术语表并包含前后文。

评价指标包括：术语 exact match、大小写和连字符保真率、中英文混合句准确率，以及术语导致的错误断句率。

### 7.3 分人质量和 ASR 质量分开评估

不能用一个“系统正常”状态替代质量评估。建议分别记录：

- ASR：CER/WER、术语召回、标点、确认延迟、修订比例；
- Diarization：DER、说话人混淆、漏检、误检和短插话误分；
- 分段：过度切分率、过度合并率、边界 precision/recall；
- 归属文本：带说话人的 WER/CER 或 WDER；
- 传输：丢字、重复、事件断档、重连补齐和 EOF 收尾。

NIST 的 Rich Transcription 评测也将“谁说了什么”、句子边界和语音识别作为不同维度处理，而不是用单一总分隐藏根因。[NIST Rich Transcription Evaluation](https://www.nist.gov/itl/iad/mltg/rich-transcription-evaluation)

## 8. 测试与验收

### 8.1 状态和协议测试

- 新会议 snapshot 到达时，旧会议的 segments、speakers、minutes、gaps 全部清除；
- 同一会议的过期事件不会覆盖新状态；
- revision 从 1 跳到 3 时立即基线同步；
- `resync_required` 必然触发 HTTP transcript 获取；
- `replace_from_ms` 等于某片段 `end_ms` 时不会重复或遗漏；
- 重连后同一文本不重复、不丢失；
- partial 不计入 confirmed 数量；
- 会议结束后 EOF 冲刷完成，最终列表和数据库一致；
- partial speaker 已知时能传递，未知时显示待确认。

### 8.2 阅读视图测试

- 同一说话人、短停顿的片段可以合并；
- 不同说话人的片段永不合并；
- 不同 `source_epoch` 的片段永不自动合并；
- 超过最大时长、字数或硬边界时强制拆分；
- 阅读块可以展开回原始 `segment_ids`；
- 时序视图和阅读视图的总文本一致。

### 8.3 质量语料

建立不写入生产数据库的受控测试语料，至少覆盖：

- 单人连续讲话；
- 两人轮流讲话；
- 一词插话和打断；
- 同时讲话；
- 专有名词密集的中英文混合会议；
- 长停顿和快速接话；
- 断线重连、事件重复和 EOF；
- 4 人以上会议。

所有质量结论应记录模型版本、参数、语料版本、评测 collar 和运行环境。

## 10. 方案取舍

### 不采用“把所有片段强行合成大段落”

这会掩盖真实说话人切换和短插话，破坏时间定位与审计能力。阅读层可以合并，但事实层必须保留原始片段。

### 不采用“看到一个词就判定 ASR 错误”

`Backfill`、`Comail` 等可能是正确业务术语，也可能是识别错误。必须用音频和金标准文本确认。

### 不采用“先换模型再验证”

当前问题同时包含事件一致性、展示语义、分段策略和领域词问题。直接换模型无法解决旧状态残留、revision 断档或不可访问控件。

### 不在本方案中引入音频存储或身份识别

这会突破既定的数据边界和匿名说话人产品决策，若未来需要音频回放或跨会议身份识别，应另行立项并重新评估隐私、权限和存储设计。

## 11. 完成标准

本方案对应的实现完成后，至少应满足：

1. 新旧会议之间不存在可见的转录、说话人或纪要串数据；
2. 任意无法解释的 revision 断档都会进入基线同步，不静默拼接；
3. 用户能区分正在识别的 partial 和已确认文本；
4. 界面不再把机器片段误称为自然段落；
5. 阅读视图不跨说话人合并，且可展开回原始时序；
6. 术语质量、分人质量和传输完整性有独立指标；
7. 重点、复制、选择和状态查看可以通过键盘和辅助技术完成；
8. 会议结束后的最终确认内容与 PostgreSQL 事实源一致。

4. 通过统一 contract version 整体联调和发布。
