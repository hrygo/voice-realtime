# ADR-005：由服务端状态机统一仲裁语音推理工作负载

## 状态

Accepted

## 日期

2026-08-25

## 背景

Voice Studio 同时包含三条会消耗本机推理资源的麦克风链路：

- 语音助手：SenseVoice → LM Studio → Qwen3-TTS；
- 实时字幕：WhisperLiveKit Qwen3-ASR → Sortformer；
- 会议助手：WhisperLiveKit Qwen3-ASR → Sortformer → PostgreSQL。

现有 `RuntimeModeCoordinator` 只管理 `assistant / meeting / idle`。实时字幕没有服务端模式，
而是由前端在切换到字幕 Tab 时尽力发送 `stop_session`，再挂载 `/ws/subtitles`。正常单浏览器路径
已经能够停止助手，但以下场景没有服务端互斥保证：

- 控制 WebSocket 尚未就绪或停止命令失败；
- 用户快速切换 Tab，字幕连接先于停止确认建立；
- 多个浏览器窗口分别启动助手和订阅字幕；
- 非前端客户端直接连接 `/ws/subtitles`；
- 模式切换失败后，前端状态与实际运行状态不一致。

2026-08-25 的本机日志还显示：WLK 进程未退出时，内部 `lag` 可从约 `0.03s` 增长到几十秒，
健康检查超时并伴随 WebSocket 清理和重连；高负载游戏会显著放大这一问题。外部负载不是应用可以
消除的条件，但应用必须避免自身在异常路径中并发运行两条重型麦克风推理链路。

本决策扩展 [ADR-001](./0001-single-owner-interaction-runtime.md) 的单一所有者原则，不取代其
进程级 `vr-ui / vr-interact` 互斥结论。

## 决策

采用服务端权威的运行时工作负载状态机：

1. `RuntimeMode` 增加 `subtitles`，全局模式固定为
   `assistant / subtitles / meeting / idle`。
2. `RuntimeModeCoordinator` 同时编排交互会话、普通字幕捕获和会议会话；所有模式切换在同一把
   `asyncio.Lock` 下执行并在成功后提交模式与 `runtime_revision`。
3. 新增控制命令 `start_subtitles`。前端必须等待服务端 ack 后再挂载字幕面板；前端 Tab 不再是
   资源所有权事实源。
4. `/ws/subtitles` 仅作为事件订阅面，不隐式停止助手或改变模式。连接只在 `subtitles` 或
   `meeting` 下接受；其他模式以稳定的模式冲突关闭码拒绝。
5. `SubtitleProxy` 增加显式的普通字幕捕获启停：
   - 应用启动只初始化代理，不自动建立永久普通字幕流；
   - 进入 `subtitles` 时建立 WLK WebSocket、等待 ready 后才提交模式；
   - 离开 `subtitles` 时停止普通字幕流并清空待发 PCM；
   - 会议捕获继续使用独占租约、EOF 冲刷和会议后端数据边界。
6. WhisperLiveKit 服务进程继续由 `run-all.sh` 外部启动并常驻预热。模式切换只控制连接和 PCM，
   不卸载模型、不重启服务，避免约 40 秒冷启动进入交互路径。
7. 任意时刻最多存在一个麦克风推理所有者：
   - `assistant`：只允许交互链路消费 PCM；
   - `subtitles`：只允许普通字幕链路消费 PCM；
   - `meeting`：只允许会议捕获链路消费 PCM；
   - `idle`：不向任何推理链路发送 PCM。
8. 模式转换采用补偿式回滚。目标工作负载未 ready 时不提交新模式；若已停止来源工作负载，则恢复
   来源工作负载。恢复也失败时进入 `idle` 并返回 `service_unavailable`，不得谎报目标模式成功。
9. 增加应用自有观测：字幕连接/ready/事件新鲜度/重连、音频丢帧和 TTS 源音频块间隔。HTTP 进程
   健康与运行时工作负载健康分开表达，不以单次 `/health` 代替 WebSocket 可用性。
10. 不自动扫描、结束或限制游戏等用户进程。主机外部负载只产生本地诊断提示，资源处置由用户决定。

## 备选方案

### 仅在前端等待停止确认后再挂载字幕

优点是改动小，能够修复单浏览器快速切换。缺点是多浏览器、非 UI 客户端和前端异常仍可绕过互斥，
资源事实源继续分散在浏览器中，因此拒绝作为最终方案。

### 让 `/ws/subtitles` 连接自动抢占助手模式

实现简单，但任意字幕客户端都能在无控制授权语义的情况下停止正在运行的助手；网络重连也可能重复
触发模式切换。事件订阅不应拥有隐式写操作，因此拒绝。

### 按模式启动、停止并卸载 WLK/TTS 服务进程

资源隔离最彻底，但会把模型冷启动带入用户切换路径，增加进程监管、失败恢复和端口所有权复杂度，
并与现有外部服务拓扑冲突。当前 128GB 统一内存不是约束，真正需要隔离的是活跃计算而非模型驻留，
因此拒绝。

### 同时运行轻量字幕 WLK 与会议 WLK 两个实例

可以分别关闭和启用说话人分离，但会复制 ASR 模型、端口、健康检查和恢复路径。现有证据尚未证明
模式仲裁完成后仍需要双实例，先按 YAGNI 推迟；若单说话人字幕在外部高负载下仍不可用，再独立立项。

## 后果

### 正向后果

- 资源互斥由服务端保证，多浏览器和控制连接异常不会产生双 ASR 并发。
- WLK 保持预热，普通模式切换不承担模型冷启动成本。
- 模式、字幕连接和服务健康不再混为同一个“已连接”状态。
- 现有会议租约、EOF、PostgreSQL 唯一事实源和零音频持久化约束保持不变。
- 外部高负载仍可能使当前唯一工作负载变慢，但不再被应用内部并发放大。

### 负向后果

- `RuntimeMode` 新增公开值 `subtitles`，前后端协议与测试必须同步更新。
- `/ws/subtitles` 在非字幕/会议模式下将明确拒绝连接，属于可观察行为变化。
- 模式切换需要定义 ready、超时、补偿回滚和多客户端语义，状态机复杂度增加。
- 普通字幕不再在应用启动时预建 WebSocket；首次进入字幕模式会增加一次连接握手，但不会重新加载模型。

### 保留风险

- 高负载游戏仍可争抢 CPU、GPU/Metal 和内存带宽；应用只能诊断，不能保证在任意外部负载下实时。
- Sortformer 在本机由 CPU 路径执行，Qwen3-ASR 使用 MPS；单一字幕工作负载仍可能同时受 CPU 和 GPU
  外部负载影响。
- TTS 预缓冲会增加首播延迟，本决策只先增加音频块节奏观测，不在无对照数据时改变缓冲策略。
